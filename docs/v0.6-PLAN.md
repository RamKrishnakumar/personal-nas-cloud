# NestDrive v0.6 — Performance Foundation & Authentication

**Status:** Planned
**Branch:** `feature/phase2-auth` → `develop` → `main`
**Supersedes:** the v0.6 section of `Roadmap.md`

---

## 0. Scope decision

`Roadmap.md` defines v0.6 as authentication and user roles only. This plan widens it to
**performance foundation + authentication**, for one reason: the current HTTP layer cannot
stream media at usable speed, and role checks have to be wired into the request path.
Restructuring the request path twice — once for auth, once for performance — costs more than
doing it once.

**In scope**

- Correct HTTP/1.1 framing, keep-alive, and byte ranges
- Multi-threaded request handling off the GUI thread
- Thumbnail and preview cache (the single largest bandwidth win)
- JSON listing API + static SPA frontend with virtual scrolling
- SQLite metadata store
- Session authentication, three roles, per-folder permissions
- Audit log
- Unit tests for the pure logic (parsing, path resolution, permissions)

**Out of scope — deferred to v0.7**

- Video transcoding and HLS (needs ffmpeg; large enough to own a release)
- Video poster frames (same dependency)
- Replacing the HTTP engine with Drogon (see §12)
- Upload / delete / create-folder *endpoints* — v0.6 defines and enforces the permission
  model, v0.8 adds the write operations that consume it

**Non-goals for this release**

- HTTP/2 or HTTP/3. Keep-alive on HTTP/1.1 recovers most of the handshake cost; the rest is
  not worth a new transport stack yet.
- Sub-100 ms cold start. Correctness and throughput first.

## 1. Decisions to confirm before starting

These three change the amount of work materially. Defaults chosen below; push back if you disagree.

| Decision | Recommended | Cost if accepted | Cost if rejected |
|---|---|---|---|
| Password hashing | **libsodium** (Argon2id) | +1 vendored dependency, ~400 KB | Qt has no PBKDF2 or Argon2 API. Rejecting means hand-rolling PBKDF2-HMAC-SHA256 over `QMessageAuthenticationCode` — doable, ~60 lines, but you own the correctness. |
| Frontend | **Static SPA** (TypeScript + Vite, no framework), embedded via `qt_add_resources` | Adds a Node build step to the release process | Keep generating HTML in C++. Blocks virtual scrolling, so folders over ~2000 files stay slow on phones regardless of what the server does. |
| Thumbnail format | **WebP**, JPEG fallback | Needs Qt's *Qt Image Formats* add-on, which was **not** installed on the dev machine — the `qwebp` plugin does not ship with the base Qt install, contrary to what this table originally assumed. | Transfer limit | **Derived from detected hardware tier, user-overridable** (§3.4.5) | A small detection routine plus one Settings control | Hardcoding 2 is correct for the reference laptop and wrong for every machine better than it. This ships to strangers. |

libsodium also supplies the CSPRNG for session tokens, so it pays for itself twice.

## 2. Constraints this design is built around

Every choice below traces back to one of these.

| Constraint | Consequence |
|---|---|
| Home **upload** bandwidth is the ceiling (asymmetric residential link, often 5–40 Mbps up) | Bytes-on-the-wire is the primary metric. Not CPU, not RAM. |
| Remote clients have high RTT (100–300 ms on mobile) | Round trips are as expensive as bytes. Kill per-request handshakes. |
| Server may be a 2-core laptop with 4 GB RAM | Bounded thread counts, bounded memory, no whole-file buffering, no content sniffing. |
| Client may be a low-end phone | Don't ship 5000 DOM nodes. Don't ship full-resolution images to a 160 px box. |
| Disk is spinning rust or a slow SATA SSD | Minimise file opens per request. Cache aggressively. Never walk a directory twice. |
| **Reference hardware is an i5 6th gen laptop, 2 cores / 4 threads, 4 GB RAM, 5400 rpm HDD** | Expensive work must be admission-controlled, not merely scheduled. See §3.4. |
| **Realistic load is 1–2 people transferring at once** | Design for that number explicitly and take the benefits, rather than building for unbounded concurrency and degrading at 3. |

**Design rule:** on any request, the server must not open a file it does not send.

**Second design rule:** bound the expensive work, not the users. Logging in, browsing, and
reading thumbnails must never be refused or queued. Streaming, uploading, and transcoding must
never be unbounded.

## 3. Architecture

### 3.1 Process and thread layout

```
┌─ MyNAS process ─────────────────────────────────────────────────────────────┐
│                                                                             │
│  GUI thread (Qt Widgets)                                                    │
│    MainWindow, TrayManager, SettingsDialog                                  │
│    HttpServer::incomingConnection()  ← accept only, never parses            │
│         │ queued signal, carries raw socket descriptor (qintptr)            │
│         ▼                                                                   │
│  ┌──────────────────────────────────────────────────────────────────────┐   │
│  │  Worker pool — N threads, N = clamp(idealThreadCount, 2, 4)          │   │
│  │  Each worker owns a QEventLoop and a set of Connection objects.      │   │
│  │  Per connection: TLS handshake, request framing, routing, streaming. │   │
│  │  All disk reads for responses happen here. Never on the GUI thread.  │   │
│  └──────────────────────────────────────────────────────────────────────┘   │
│         │ async job submit                     │ mutex-guarded              │
│         ▼                                      ▼                            │
│  ┌──────────────────────┐            ┌───────────────────────────────────┐  │
│  │ Thumbnail pool       │            │ Database (single connection)      │  │
│  │ 1 thread (2 if ≥4    │            │ SQLite, WAL, guarded by QMutex    │  │
│  │ cores), LowPriority  │            │ users, sessions, perms, thumbs,   │  │
│  │ + idle Scanner       │            │ files, audit, scan_state          │  │
│  └──────────────────────┘            └───────────────────────────────────┘  │
│                                                                             │
│  DdnsUpdater — GUI thread, timer-driven, unchanged                          │
└─────────────────────────────────────────────────────────────────────────────┘
```

Worker count is capped at 4 deliberately. File serving is I/O-bound; on a 2-core laptop more
threads add context switching and memory without adding throughput.

### 3.2 Why this fixes the accept path

Current code, in `FileServer::onNewConnection()`, creates a `QTcpSocket`, steals its
descriptor, then calls `setSocketDescriptor(-1)` to stop the original from closing the
descriptor on destruction. That dance exists only because `QTcpServer::nextPendingConnection()`
hands back a socket you didn't want.

Override `incomingConnection(qintptr handle)` instead. Qt then never constructs a socket at
all — you receive the raw descriptor and hand it to a worker, which constructs the
`QSslSocket` in its *own* thread and adopts the descriptor there. This removes the
descriptor-stealing hack, and it is the only way to get the socket living in the worker
thread from birth (moving a connected `QSslSocket` between threads mid-handshake is not safe).

### 3.4 Admission control — the concurrency model

This is the section that makes the reference hardware viable. Read it before §4.

#### 3.4.1 What "2 users at a time" must not mean

Three different things get conflated, and limiting the wrong one breaks the product:

| Candidate limit | Effect if set to 2 | Verdict |
|---|---|---|
| Concurrent TCP connections | **Breaks a single browser tab.** Chrome opens 6 connections per origin for parallel thumbnails. One user would exhaust the limit against themselves. | Wrong layer |
| Concurrent logged-in sessions | Logging in on a phone silently evicts the laptop. Sessions cost two database rows; they burden nothing. | Pointless |
| Concurrent **active transfers** | Bounds disk seeking, upload bandwidth, and memory — the three things that actually make the machine lag. | **Correct** |

The limit belongs on transfers. Everything else stays unbounded.

#### 3.4.2 Resource classes

Each class of work gets its own budget, sized to what it actually costs:

| Class | What it costs | Limit | Queued? |
|---|---|---|---|
| Control — login, `/api/list`, `/_static/*`, `304`s | Microseconds, no disk | None | Never |
| Thumbnail cache **hit** | One 20 KB sequential read | None | Never |
| Thumbnail cache **miss** (decode) | 30–150 ms CPU | Thumbnail pool: 1 thread (2 if ≥4 cores) | Yes, inside the pool |
| Small file, under 2 MB | One short read, completes in a blink | None | Never |
| **File stream ≥ 2 MB** — download or playback | Sustained disk + the whole upload link | **2 slots** + 1 reserved for admin | Yes, 10 s then `503` |
| Upload (v0.8) | Disk write + hashing | 1 slot | Yes |
| Transcode (v0.7) | GPU or CPU, heavily | 1 slot, hard | Yes |

Browsing a folder of 500 photos on a cold cache therefore consumes **zero** transfer slots. It
is bounded by the thumbnail pool, which already existed. Two people can browse freely while a
third downloads a movie.

The 2 MB threshold matters: queueing a 200 KB file behind admission control adds latency for no
saving. Only sustained transfers take a slot.

#### 3.4.3 Slots are held per session, not per connection

```cpp
// RAII. Released on scope exit, on client abort, and by the watchdog.
class StreamSlot {
public:
    static std::optional<StreamSlot> tryAcquire(SessionId, Role, qint64 fileSize);
    ~StreamSlot();                      // always releases
};
```

Rules:

- A slot is keyed by **session**, so one person watching a video while their browser also
  fetches thumbnails holds one slot, not seven.
- A session may hold at most **2** concurrent streams. A browser downloading 6 files in
  parallel serialises into 2 — which costs nothing, because total time is bandwidth-bound
  anyway, and it converts 6 interleaved read heads into 2.
- **Range requests on a file the session is already streaming reuse that session's existing
  slot.** Without this rule, video seeking deadlocks against the limit: the player closes its
  connection, opens a new one with a `Range` header, and queues behind its own held slot.
  This is the single most important detail in the section.
- `admin` has one **reserved** slot above the shared pool. The owner of the machine is never
  locked out of their own storage by guests.

#### 3.4.4 Failure modes to design against

| Failure | Cause | Mitigation |
|---|---|---|
| **Slot leak** — server wedges permanently after a few aborted downloads | Client vanishes mid-stream; `disconnected` never fires cleanly on a dead mobile connection | RAII release, plus a 30 s watchdog reclaiming slots whose socket is no longer writable. Test this explicitly — it is the one bug that turns the limit into a denial of service against yourself. |
| Third user sees a hang | Queued with no feedback | Queue up to 10 s, then `503` + `Retry-After: 5`. The client shows "Waiting for a free transfer slot — 1 ahead of you". A visible queue reads as a working system; a stall reads as broken. |
| Starvation | One user streams a 40 GB file for an hour | Accepted in v0.6. Slots are long-held by design, the queue has a timeout, and admin has a reserved slot. Fair bandwidth sharing is a v0.8 question, and only if it proves necessary. |

#### 3.4.5 The limit is derived, then overridable

Do not hardcode 2. This ships to strangers' machines, and someone installing on a Ryzen with a
1 Gbps symmetric link should not be throttled to a 2016 laptop's budget.

At first run, detect a tier and set defaults:

| Tier | Detection | Workers | Thumb threads | Stream slots | Read chunk |
|---|---|---|---|---|---|
| Light | ≤2 physical cores, or ≤4 GB RAM, or HDD detected | 2 | 1 | **2** | 1 MB |
| Balanced | 4 cores, ≥8 GB RAM, SSD | 3 | 2 | 4 | 512 KB |
| Capable | ≥8 cores, ≥16 GB RAM, SSD | 4 | 2 | 8 | 512 KB |

The reference i5 6th gen laptop lands in **Light**, which is exactly the behaviour you asked
for — reached by derivation rather than assertion, so the product still works on better
hardware.

Settings exposes **Maximum simultaneous transfers**: `Auto` (default) / 1 / 2 / 4 / Unlimited,
with the detected tier shown next to it. Detection heuristics are always wrong for someone.

### 3.5 What the concurrency cap buys you

Bounding concurrency is not only a restriction — three optimisations become available *because*
the bound exists, and all three matter most on the slowest hardware.

**Larger sequential reads.** The current 256 KB chunk is a compromise for unbounded
concurrency. On a 5400 rpm HDD with a ~10 ms seek, four interleaved streams at 256 KB
thrash the head; measured throughput can collapse from ~100 MB/s sequential to 10–20 MB/s. With
at most 2 streams, raise the chunk to **1 MB**: seek overhead amortises roughly 4× better and
the access pattern stays near-sequential. This single change may matter more on an HDD than
everything in §4 combined.

**Provable memory ceiling.** 2 streams × 1 MB chunk + 512 KB socket buffer ≈ 3 MB of transfer
buffers, worst case. Not an estimate — an arithmetic bound. It is what makes the <120 MB RSS
target in §11.2 a guarantee rather than a hope.

**Smaller worker pool.** At most 2 streams plus cheap control traffic means 2 worker threads
suffice on the reference machine. On an i5-6200U (2 cores / 4 threads) that leaves headroom for
the GUI, the thumbnail thread, and the OS. A pool sized for unbounded load would spend its time
context-switching.

## 4. HTTP layer

### 4.1 Request framing

`handleRequest()` today calls `readAll()` once and assumes the entire request arrived in that
read. On a slow or TLS-wrapped link, headers split across reads and the parse fails.

Replace with a per-connection accumulator:

```cpp
class Connection : public QObject {
    enum class State { ReadingHeaders, ReadingBody, Streaming, Closing };

    QTcpSocket* m_socket;       // QSslSocket in HTTPS mode
    QByteArray  m_inBuf;
    State       m_state = State::ReadingHeaders;
    Request     m_req;
    qint64      m_bodyRemaining = 0;
    int         m_requestsServed = 0;
    QTimer      m_idleTimer;    // 15 s, reset on every read
};
```

On `readyRead`: append to `m_inBuf`, then loop — a single read can contain a complete request,
part of one, or several pipelined ones.

Limits, all enforced:

| Limit | Value | Response on breach |
|---|---|---|
| Header block size | 16 KB | `431 Request Header Fields Too Large` |
| Request line length | 8 KB | `414 URI Too Long` |
| Requests per connection | 200 | close after response |
| Idle between requests | 15 s | close |
| TLS handshake | 8 s | close |
| Concurrent connections | 32 (Light tier) | `503 Service Unavailable`, `Retry-After: 2` |
| Concurrent streams ≥2 MB | 2 + 1 admin reserve | queue 10 s, then `503` (§3.4) |

Two distinct caps, doing two distinct jobs. The **connection** cap stops a port scanner from
opening 5000 sockets on a 4 GB machine; it is set well above what any real browser needs, since
one tab uses about 6. The **stream** cap in §3.4 is what protects the disk and the upload link.
Conflating them would break normal browsing.

### 4.2 Keep-alive

This is the highest-leverage change in the release.

A 60-thumbnail folder currently costs 60 TCP connections and 60 TLS handshakes. A TLS 1.2
handshake is roughly 3 round trips; at 150 ms RTT that is about 450 ms of setup per image, and
the browser only runs 6 in parallel. Roughly 4.5 seconds of pure handshake before the last
thumbnail even starts transferring — and that is before any image bytes move.

With keep-alive the same page uses about 6 connections total and 6 handshakes.

Implementation:

- HTTP/1.1 is keep-alive by default. Honour it unless the request sends `Connection: close`.
- Always send an accurate `Content-Length`, or use chunked encoding. Without exact framing,
  keep-alive corrupts the next response on the same connection. This is why §4.3 matters.
- Respond `Connection: keep-alive`; close on HTTP/1.0 unless the client asked to persist.
- Delete the `QObject::disconnect(socket, &QTcpSocket::readyRead, nullptr, nullptr)` call in
  `sendFile()`. With a state machine, `Streaming` state already ignores incoming bytes —
  tearing down the signal is unnecessary and breaks reuse.

### 4.3 Byte ranges — correct implementation

Current `parseRangeStart()` reads only the start offset and returns `-1` otherwise. Two
consequences:

- `Range: bytes=0-1` (the probe a video element sends first) has start `0`, fails the
  `rangeStart > 0` test, and falls through to a **full 200 response**. The browser asked for
  2 bytes and receives the entire file.
- `Range: bytes=100-200` streams from byte 100 to end of file, while `Content-Range` claims
  the same. Every seek pulls the remainder of the video.

Replace with a pure function, unit-tested:

```cpp
struct ByteRange { qint64 start; qint64 end; bool valid; bool satisfiable; };

// Handles:  bytes=a-b   → [a, min(b, size-1)]
//           bytes=a-    → [a, size-1]
//           bytes=-n    → [max(0, size-n), size-1]     (suffix range)
//           multiple ranges → serve the first only
// start >= size → unsatisfiable
ByteRange parseRange(QByteArrayView headerValue, qint64 fileSize);
```

Response rules:

- Satisfiable → `206 Partial Content`, `Content-Range: bytes S-E/SIZE`,
  `Content-Length: E-S+1`
- Unsatisfiable → `416 Range Not Satisfiable`, `Content-Range: bytes */SIZE`
- No `Range` header → `200 OK`, full length
- Always advertise `Accept-Ranges: bytes`

The streaming pump must count down `bytesRemaining = end - start + 1` and stop there. The
current pump loops on `file->atEnd()`, which is why a partial request drains the whole file
even when the header says otherwise.

### 4.4 MIME type

`getMimeType()` uses `QMimeDatabase::mimeTypeForFile()` with default flags, which opens each
file and sniffs its content. It is called twice per directory entry — once building the media
index, once building the cards. A 500-file folder performs about 1000 file opens before the
first byte of HTML is sent.

Fix: `db.mimeTypeForFile(path, QMimeDatabase::MatchExtension)`, resolved **once** per entry
and carried in the entry struct. Zero file opens.

### 4.5 Compression

`gzipCompress()` is dead code, and `qCompress` produces a zlib stream with a 4-byte
big-endian length prefix — not valid for `Content-Encoding: deflate` or `gzip`. Shipping it
would have broken every client.

zlib is already a Qt dependency, so link it directly and wrap it properly:

```cpp
// windowBits = 15 | 16 selects the gzip container rather than raw zlib
deflateInit2(&zs, 6, Z_DEFLATED, 15 | 16, 8, Z_DEFAULT_STRATEGY);
```

Compress only when the client sends `Accept-Encoding: gzip` **and** the content type is
compressible: `text/*`, `application/json`, `application/javascript`, `image/svg+xml`.
Never compress JPEG, WebP, MP4, or ZIP — it burns CPU on a weak machine for a rounding error.

### 4.6 Caching headers

| Resource | Header | Rationale |
|---|---|---|
| `/_thumb/*` | `Cache-Control: public, max-age=31536000, immutable` | The URL embeds file mtime and size, so a changed file produces a different URL. Safe to cache forever. |
| `/_static/*` | `Cache-Control: public, max-age=31536000, immutable` | Content-hashed filenames from the Vite build |
| `/files/*` | `Cache-Control: private, max-age=3600` + `ETag` | Private: responses depend on the session |
| `/api/list` | `Cache-Control: no-store` | Listings must never be stale |
| `/login` | `Cache-Control: no-store` | |

`Vary: Accept-Encoding` on every compressed response, or intermediate caches will serve
gzipped bytes to a client that cannot decode them.

Keep the existing `ETag` / `304` path — it is correct. Note the ETag is derived from path +
mtime + size, so it changes when the file changes but not when only permissions change. That
is the behaviour you want.

## 5. Thumbnail and preview cache

The largest single win in this release. A grid of 60 phone photos currently transfers roughly
**300 MB** to paint sixty 160×110 boxes, because the `<img src>` points at the original file.

### 5.1 Two tiers

| Tier | Long edge | Format / quality | Typical size | Used for |
|---|---|---|---|---|
| `s` | 320 px | WebP q72 | 15–25 KB | Grid cards |
| `m` | 1280 px | WebP q80 | 80–150 KB | Overlay preview |

Tier `m` matters as much as `s`. Right now, opening one photo in the overlay downloads the
full original — 5 MB for a look at a phone snapshot. Tier `m` makes that about 120 KB. The
Download button keeps pointing at the original, so nothing is lost.

AVIF would be smaller still, but encoding it is slow on a weak CPU. Rejected for that reason.

### 5.2 Storage layout

```
<QStandardPaths::CacheLocation>/thumbs/<first 2 hex of key>/<key>.webp
```

Key: `md5(canonicalPath | mtimeMs | size | tier)`, hex.

The two-character shard directory is not cosmetic — 100,000 files in one directory makes
directory enumeration pathological on both NTFS and ext4.

Including `mtimeMs` and `size` in the key means a modified file produces a new key
automatically. No invalidation logic, and it is what makes `immutable` caching safe in §4.6.

Cache location is configurable. Default to `CacheLocation` (usually the system SSD), which is
typically faster than the NAS spindle.

### 5.3 Generation — fast path

Do **not** decode a 12-megapixel JPEG to produce a 320 px thumbnail.

```cpp
QImageReader reader(sourcePath);
reader.setAutoTransform(true);                 // honour EXIF orientation
reader.setScaledSize(fittedSize(reader.size(), longEdge));
QImage img = reader.read();
```

For JPEG, `setScaledSize` lets libjpeg use scaled DCT decoding (1/2, 1/4, 1/8), which is
roughly 5–8× faster than a full decode and uses proportionally less memory. This is built into
Qt; it needs no dependency. `setAutoTransform(true)` is what stops portrait photos appearing
sideways.

Check `QImageWriter::supportedImageFormats()` once at startup. If `webp` is absent from the
build, fall back to JPEG q80 and log it.

### 5.4 Generation — never block a worker

On cache miss the worker must not park waiting for a decode. With 4 workers and 60 misses you
would serialise the whole page.

```
GET /_thumb/s/<path>
   │
   ├─ hit  → stream the cached file (immutable headers)
   │
   └─ miss → ThumbnailCache::requestAsync(key, callback)
              │
              ├─ job already in flight for this key → attach callback, return
              └─ else enqueue on the thumbnail pool
              │
              worker returns immediately; no thread parked
              │
              on completion → callback invoked on the worker's thread
                              via queued connection → response sent
```

Coalescing in-flight jobs by key matters: two browser tabs on the same folder must not decode
the same image twice.

If a job fails or exceeds 10 s, respond `302` to a static placeholder SVG.

### 5.5 Background warming

First visit to a cold folder is still slow, because every thumbnail is a miss. Fix it before
the user arrives.

- An idle `Scanner` walks `nasRoot` and generates tier `s` thumbnails ahead of demand.
- One thread, `QThread::LowPriority`.
- **Pauses entirely while any client is streaming.** A warm-up job must never compete with the
  person trying to watch a video. Gate it on `AdmissionControl`'s active-stream count (§3.4) —
  that counter already exists and is authoritative, so no separate bookkeeping is needed.
- Progress persists in `scan_state`, so a restart resumes rather than rescanning.
- Also pause on battery power (`QBatteryInfo` / platform check) — this runs on a laptop.

### 5.6 Eviction

Cap total cache size, default 2 GB, configurable. On startup and every 6 hours, if over cap,
delete least-recently-used entries (`thumbs.last_used_at`) down to 80% of the cap.

### 5.7 Video and HEIC — decided 2026-10-01

Both are the same problem: extracting a still image from a file Qt's image plugins cannot
read. Qt Image Formats does not include HEIF, so iPhone photos have no thumbnail either.

**Decision: bundle the ffmpeg CLI and shell out to it.** Simplest to implement and debug, one
dependency covers HEIC stills, video poster frames and later transcoding, and it is what
Jellyfin and Immich both do. Cost is roughly 80 MB in the installer and a subprocess per
thumbnail — acceptable, since generation is cached and happens once per file.

Rejected: linking FFmpeg directly (Qt ships only the runtime DLLs, so matching dev packages
would have to be sourced per compiler and platform, for a per-thumbnail saving nobody will
notice at this scale), and QMediaPlayer frame grabbing (built for playback, asynchronous,
historically unreliable for seek-and-grab, and no help for HEIC).

**Sequencing: after step 12**, so gzip and the SPA land first — those matter more for large
folders and slow links. Until then, undecodable images show a neutral placeholder rather than
a broken-image icon, and videos keep the 🎬 card.

Range support (§4.3) already makes direct playback correct for browser-compatible files.
Incompatible codecs still will not play, which is what v0.7 addresses.

## 6. Listing API and frontend

### 6.1 Why the server stops generating HTML

A 5000-file folder rendered as HTML by string concatenation is roughly 1.5 MB, and the phone
must build 5000 DOM nodes. Both ends suffer.

As JSON it is about 300 KB, roughly 60 KB gzipped, and with virtual scrolling the browser
builds about 40 nodes regardless of folder size. That is the low-end-client win, and it cannot
be had from C++ string building.

### 6.2 Endpoint

```
GET /api/list?path=/Photos/2024&offset=0&limit=200&sort=name&order=asc

200 OK
Content-Type: application/json
Content-Encoding: gzip
Cache-Control: no-store

{
  "path": "/Photos/2024",
  "total": 4821,
  "offset": 0,
  "limit": 200,
  "perm": { "read": true, "write": false, "delete": false },
  "entries": [
    { "n": "IMG_0421.jpg", "d": false, "s": 4812304, "m": 1727... ,
      "k": "image", "t": "/_thumb/s/a1b2c3d4e5f6..." },
    { "n": "Trip", "d": true }
  ]
}
```

Notes:

- Short keys. At 5000 entries, field names are a measurable fraction of the payload.
- `t` is the thumbnail URL with the key already computed, so the client never derives it.
- `perm` is resolved server-side. The client uses it to hide unavailable actions; the server
  still re-checks on every mutating request. UI hiding is presentation, never enforcement.
- `d` (isDir), `s` (size), `m` (mtime), `k` (kind: `image`/`video`/`file`).

### 6.3 Escaping

Filenames are currently interpolated raw into both HTML and the JS media index. A file named
`a"b.jpg` breaks the index; `<img onerror=...>` in a filename is stored XSS.

Moving to JSON plus a client that sets `textContent` removes the whole class of problem — as
long as the JSON is produced by `QJsonDocument`, never by string concatenation. No exceptions.

### 6.4 Frontend

TypeScript + Vite, no framework. Built assets embedded via `qt_add_resources`, served from
`/_static/*` with content-hashed filenames.

## 7. Data model

SQLite, WAL mode, one connection guarded by a `QMutex`. At NAS scale — a handful of users,
single-digit requests per second — a mutex-guarded connection is simpler and lower-memory
than per-thread connections, and it sidesteps the Qt rule that `QSqlDatabase` connections
cannot be shared across threads.

```sql
PRAGMA journal_mode = WAL;      -- readers don't block the writer
PRAGMA synchronous  = NORMAL;   -- fsync less; acceptable for a cache + audit store
PRAGMA busy_timeout = 5000;
PRAGMA foreign_keys = ON;

CREATE TABLE users (
  id          INTEGER PRIMARY KEY,
  username    TEXT    NOT NULL UNIQUE,
  pw_hash     TEXT    NOT NULL,         -- Argon2id encoded string
  role        TEXT    NOT NULL CHECK (role IN ('admin','family','guest')),
  enabled     INTEGER NOT NULL DEFAULT 1,
  created_at  INTEGER NOT NULL,
  last_login_at INTEGER
);

-- Longest matching path_prefix wins. Guests have no implicit access.
CREATE TABLE folder_perms (
  user_id     INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  path_prefix TEXT    NOT NULL,          -- NAS-relative, normalised, leading '/'
  perm        TEXT    NOT NULL CHECK (perm IN ('none','read','write')),
  PRIMARY KEY (user_id, path_prefix)
);

CREATE TABLE sessions (
  token_hash  BLOB    PRIMARY KEY,       -- SHA-256 of the token; raw token never stored
  user_id     INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  created_at  INTEGER NOT NULL,
  last_seen_at INTEGER NOT NULL,
  expires_at  INTEGER NOT NULL,
  ip          TEXT,
  user_agent  TEXT
);
CREATE INDEX idx_sessions_expiry ON sessions(expires_at);

CREATE TABLE thumbs (
  key          TEXT PRIMARY KEY,
  src_path     TEXT NOT NULL,
  mtime_ms     INTEGER NOT NULL,
  size         INTEGER NOT NULL,
  tier         TEXT NOT NULL CHECK (tier IN ('s','m')),
  bytes        INTEGER NOT NULL,
  created_at   INTEGER NOT NULL,
  last_used_at INTEGER NOT NULL
);
CREATE INDEX idx_thumbs_lru ON thumbs(last_used_at);

-- Ownership for the "delete own files only" rule (v0.8 consumes this)
CREATE TABLE files (
  path        TEXT PRIMARY KEY,          -- NAS-relative
  uploaded_by INTEGER REFERENCES users(id) ON DELETE SET NULL,
  uploaded_at INTEGER NOT NULL
);

CREATE TABLE scan_state (
  path    TEXT PRIMARY KEY,
  done_at INTEGER NOT NULL
);

CREATE TABLE audit (
  id      INTEGER PRIMARY KEY,
  ts      INTEGER NOT NULL,
  user_id INTEGER REFERENCES users(id) ON DELETE SET NULL,
  action  TEXT    NOT NULL,   -- login, login_fail, logout, list, download, upload, delete, mkdir
  path    TEXT,
  bytes   INTEGER,
  status  INTEGER,            -- HTTP status
  ip      TEXT
);
CREATE INDEX idx_audit_ts ON audit(ts);
```

Schema versioning via `PRAGMA user_version`, applied by a `Migrations` class at startup. Set
it to 1 in this release so v0.7 has somewhere to go.

Known limitation, accepted: `files.path` is keyed by path, so renaming a file outside the app
orphans its ownership row. Acceptable for v0.6; revisit if it bites.

## 8. Authentication

### 8.1 Passwords

`Roadmap.md` proposes "bcrypt or Qt-based SHA-256 + salt". **SHA-256 + salt is not adequate**
for password storage — it is fast by design, which is precisely wrong here. A GPU tries
billions of SHA-256 candidates per second.

Use Argon2id via libsodium:

```cpp
crypto_pwhash_str(out, password, len,
                  opslimit,   // 2
                  memlimit);  // 19 MiB  (OWASP: m=19456 KiB, t=2, p=1)
```

libsodium's `INTERACTIVE` preset asks for 64 MiB, which is a lot to allocate briefly on a
4 GB machine. The OWASP parameters (19 MiB, 2 passes) are the better fit here and are still
far beyond anything a fast hash offers.

Verification: `crypto_pwhash_str_verify`. No manual comparison, no timing concerns.

### 8.2 Sessions

- Token: 32 bytes from `randombytes_buf`, base64url-encoded.
- **Store only `SHA-256(token)`.** A database leak then does not hand over live sessions.
- Cookie: `Set-Cookie: nd_session=<token>; HttpOnly; SameSite=Lax; Path=/` plus `Secure`
  whenever HTTPS is active.
- Expiry: 12 hours idle default; 14 days when "remember me" is checked. Refresh
  `last_seen_at` on use, but write at most once per minute per session to avoid a DB write on
  every thumbnail request.
- Logout deletes the row. A sweep on startup and hourly deletes expired rows.

`HttpOnly` is what stops a stored-XSS bug from becoming account takeover — which is the same
class of bug §6.3 closes from the other direction.

### 8.3 Login rate limiting

Two independent in-memory buckets, no DB write on the hot path:

- 5 failures per username per 15 minutes
- 20 failures per source IP per 15 minutes

On breach: `429 Too Many Requests` with `Retry-After`. Log to `audit` as `login_fail`.

Return an identical error message and an identical response time for "no such user" and "wrong
password". Distinguishing them tells an attacker which usernames exist.

### 8.4 Gate placement

Exactly one gate, in the router, before any handler runs:

```
Public:  /login (GET, POST), /_static/*, /favicon.ico, /healthz
Everything else: valid session required, else 302 /login?next=<url>
                 (401 with a JSON body when the request accepts JSON)
```

No handler may serve bytes before the gate. Enforce this by construction: handlers receive an
`AuthContext` parameter that only the router can produce.

## 9. Authorisation

### 9.1 Role matrix

Per your specification:

| Role | Read | Upload | Create folder | Delete | Settings |
|---|---|---|---|---|---|
| admin | all | yes | yes | any file | yes |
| family | all | yes | yes | own uploads only | no |
| guest | only listed folders | only where granted | only where write granted | never | no |

### 9.2 Resolution

One pure function. No filesystem access, no database access — inputs in, decision out, so it
is fully unit-testable:

```cpp
struct Perm { bool read; bool write; bool remove; };

Perm resolve(const UserRecord& user,
             const QList<FolderPerm>& perms,   // that user's rows, pre-loaded
             const QString& nasRelativePath,
             std::optional<int> fileOwnerId);
```

Rules, in order:

1. `enabled == 0` → all false
2. Longest matching `path_prefix` wins. `/Photos/2024` beats `/Photos` beats `/`.
3. Explicit `none` denies, even under a permitting ancestor. Deny is not overridable by
   a shorter prefix.
4. No match: admin and family get read+write; **guest gets nothing**. Deny by default is what
   makes the guest role actually a guest.
5. `remove`: admin always; family only when `fileOwnerId == user.id`; guest never.

Path normalisation happens before resolution and is itself a tested pure function (§10).

Every handler calls `resolve()`. The client's cached `perm` from §6.2 is advisory only.

## 10. Path safety

Current guard:

```cpp
const QString fsPath = QDir::cleanPath(nasRoot + "/" + urlPath);
if (!fsPath.startsWith(nasRoot)) { /* 403 */ }
```

Two defects:

1. **Prefix collision.** With `nasRoot = "E:/Foo"`, the path `E:/Foobar` passes `startsWith`.
   A sibling directory escapes.
2. **Windows case-insensitivity.** `e:/foo/...` does not match `E:/Foo` under a case-sensitive
   `startsWith`, so legitimate requests 403 — and any case-folding fix must be applied on the
   comparison, not the stored root.

Replacement, as a tested pure-ish function:

```cpp
// Returns absolute filesystem path, or nullopt if the request escapes the root.
std::optional<QString> resolveSafe(const QString& nasRoot, const QString& urlPath);
```

1. Percent-decode once. Reject a second `%` round that changes the string (double encoding).
2. Reject NUL bytes and, on Windows, reject `:` outside the drive prefix (NTFS alternate data
   streams) and the reserved device names `CON`, `PRN`, `AUX`, `NUL`, `COM1-9`, `LPT1-9`.
3. Normalise separators, collapse `.` and `..` **before** touching the filesystem.
4. Compare using `QDir::cleanPath` on both sides, with the root guaranteed to end in `/`, so
   the prefix test cannot collide.
5. Case-insensitive comparison on Windows and macOS; case-sensitive on Linux.
6. Then `QFileInfo::canonicalFilePath()` and re-check the prefix — this is what catches
   symlinks and NTFS junctions pointing outside the root. The cheap checks come first so the
   expensive syscall only runs on paths that already look valid.

Steps 3 and 6 are both necessary. Step 3 catches traversal before any I/O; step 6 catches
links, which no amount of string normalisation can see.

### 11.2 Server budget on the reference i5 6th gen laptop (2c/4t, 4 GB, HDD)

| Resource | Target | Enforced by |
|---|---|---|
| Steady RSS | <120 MB | Stream cap × chunk size is an arithmetic bound (§3.5) |
| Transfer buffers, worst case | ~3 MB | 2 streams × 1 MB chunk + 512 KB socket buffer |
| CPU, 2 clients browsing a cold folder | <25% of one core | Thumbnail pool is 1 thread; no content sniffing; no needless compression |
| CPU, 2 clients streaming | <10% of one core | Streaming is disk and socket copying, not computation |
| Worker threads | 2 (Light tier) | Tier detection (§3.4.5) |
| Thumbnail threads | 1 (Light tier) | Tier detection |
| Concurrent streams | 2 + 1 admin reserve | Admission control (§3.4) |
| Concurrent connections | 32 | 503 beyond |
| Disk read pattern | near-sequential | 1 MB chunks × at most 2 streams (§3.5) |
| Thumbnail cache on disk | 2 GB default | LRU eviction (§5.6) |
| GUI responsiveness while streaming | no visible lag | Serving is off the GUI thread entirely (§3.1) |

Two numbers here are guarantees rather than goals: the transfer-buffer figure and the thread
counts. Both follow directly from the admission bound, which is why §3.4 comes before the
performance work rather than after it.

### 11.3 One GUI-side fix

`QFileSystemModel` in `MainWindow` is pointed at the NAS root and watches it. On a multi-
terabyte drive that accumulates file-system watchers and memory for no benefit — the desktop
window is not the primary interface. Either disable watching, or replace the tree with a
plain "open in Explorer / Finder" button. Low effort, meaningful RAM saving on the machine
that is also serving files.

## 12. What this release deliberately does not change

**The HTTP engine stays `QTcpServer`.** Adopting Drogon would mean re-plumbing TLS, routing,
and static file serving at the same time as introducing authentication — two risky changes in
one release, with no way to tell which one broke something.

Every item in §4 is a correctness or structural fix that Drogon would give you for free later.
None of them is wasted: the handlers, the permission model, the thumbnail cache, the database,
and the frontend are all engine-independent. Revisit the engine at v0.8 with real throughput
numbers in hand rather than a guess.

Similarly, HTTP/2 is skipped. Its main benefit over HTTP/1.1 keep-alive is multiplexing, which
matters for hundreds of tiny requests. Once thumbnails are 20 KB and connections are reused,
the remaining win is small relative to the cost of a new transport stack.

## 16. Remote access — recommendation for v0.7 onward

Not part of this release, recorded here because it affects the v1.0 install story.

Port forwarding plus DDNS puts the server on the public internet and asks every user to
configure their router. That is the hardest part of the current setup, and it is also the
riskiest.

WireGuard, or Tailscale as a managed layer over it, removes all of that: no inbound port, no
router configuration, no public exposure, and real TLS certificates rather than a self-signed
certificate that makes browsers warn. Keep port forwarding as an advanced option for users who
want genuinely public sharing.

Worth evaluating before v1.0, since it changes what the setup wizard needs to teach.

## 17. Hardware tiers and the GPU question

Recorded here because it constrains v0.7's design, and because one common assumption about the
reference machine is probably backwards.

### 17.1 On an i5 6th gen laptop, the integrated GPU is likely the better encoder

Skylake's integrated graphics include **Quick Sync**: fixed-function H.264 encode and decode,
plus HEVC 8-bit decode. For transcoding 1080p H.264 — which is the overwhelming majority of what
a personal photo and video library needs — that is sufficient, and it has three advantages over a
discrete card on this specific machine:

- It draws a few watts instead of tens. On a laptop that means less heat, quieter fans, and
  crucially **less thermal throttling of the CPU cores that are also serving HTTP**. A discrete
  GPU spinning up is itself a cause of the lag this plan is trying to eliminate.
- It needs no separate VRAM budget.
- Zero-copy paths between decode, scale, and encode are well supported through VAAPI on Linux and
  D3D11VA / QSV on Windows.

A 2 GB card of that era is a genuine unknown until identified. Depending on the exact model it
may have first-generation NVENC with visibly poor quality at low bitrates, or — on some low-end
parts of that period — no hardware encoder at all. 2 GB of VRAM is enough for one or two 1080p
sessions, and 4K HEVC decode may be unsupported entirely.

**Action before v0.7 begins:** identify the card (`nvidia-smi`, or Device Manager) and run
`ffmpeg -hwaccels` plus a real 1080p encode on both engines. Choose based on measurement. Do not
assume the discrete card wins because it is discrete.

### 17.2 The hardware caps concurrency independently

Worth knowing, because it corroborates the §3.4 limit from a different direction: NVIDIA's
consumer drivers have historically capped concurrent NVENC sessions — 2 for many years, raised in
later driver generations. Quick Sync has no hard session cap but degrades below real time quickly
once more than one or two 1080p streams are in flight on a Skylake part.

So a transcode limit of 1–2 is not a conservative product decision layered on top of capable
hardware. It is roughly what the silicon actually delivers. The plan's **1 transcode slot on the
Light tier** matches the hardware rather than constraining it.

### 17.3 Encoder selection order for v0.7

Probe at startup, cache the result, expose it read-only in Settings:

1. Quick Sync (`h264_qsv`) where the iGPU is present and available — preferred on laptops
2. NVENC (`h264_nvenc`) where a capable discrete GPU is present and measurably better
3. VideoToolbox on macOS, VAAPI on Linux
4. CPU `libx264 -preset veryfast` as the universal fallback, **with the transcode slot forced
   to 1** — software encoding on two cores while also serving files will make the machine lag,
   which is precisely the outcome this document exists to prevent

Rule for v0.7: **direct-play whenever possible.** If the file is already H.264/AAC in MP4 and its
bitrate fits the link, stream the bytes and transcode nothing. On the reference hardware, the
cheapest transcode is the one that does not happen — and with the correct range support from §4.3,
direct play finally works properly.
